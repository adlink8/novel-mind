# Phase 25.3: Pi Package Compatibility and Governance - Research

**Researched:** 2026-08-01
**Domain:** npm supply-chain governance (lock/audit/scan), permission policy engines (allow/ask/deny), MCP adapter isolation, web-UI renderer feasibility
**Confidence:** HIGH (all three packages re-verified against npm registry + official READMEs/docs this session; NovelMind-side seams carried over from verified 25.2 research)

## Summary

All three D-03 verdicts survive re-validation. `pi-mcp-adapter@2.17.0` (MIT, ~88k downloads/week, no lifecycle scripts) ships exactly the isolation primitive D-07 needs: `createMcpAdapter({ config })` is a **complete, isolated snapshot** that "is not merged with files, imports, global config, project config... and it is never mutated" — ambient user-machine MCP config is excluded by construction, and servers are lazy by default with a single ~200-token proxy tool. `@gotgenes/pi-permission-system@24.0.0` (MIT) has superbly documented *semantics* — last-match-wins inside a surface, most-restrictive-wins across layers, fail-closed clamps, session-scoped approvals, restrict-only tool-visibility filtering — but its *implementation* is welded to Pi lifecycle hooks (`before_agent_start`/`tool_call`/`input`), TUI keybind dialogs, `~/.pi` config paths, and tree-sitter bash parsing. None of that serves domain-action policy over a web API; the recommendation is **clean-room reimplementation of the precedence semantics (~250 lines), not a fork**. `@earendil-works/pi-web-ui@0.75.3` confirms the "selective/pattern-only" verdict: it lags the SDK (0.75.3 vs 0.83.0, depends on `^0.75.3` pi-ai/pi-tui), drags heavy browser deps (pdfjs-dist, an xlsx CDN tarball, jszip, ollama, @lmstudio/sdk), and its session authority (ChatPanel + IndexedDB stores + browser-held provider keys) is precisely what D-15 and the 25.2 architecture forbid — but its `registerToolRenderer` / `registerMessageRenderer` / compact-tool-result patterns are directly borrowable as React designs.

The governance pipeline itself needs almost no new technology: npm already provides `npm ci --ignore-scripts`, `npm audit --json`, and `npm audit signatures`; one maintained license scanner (`license-checker-rseidelsohn@5.0.1`, dev-only) plus a small custom Node scanner (lifecycle scripts, dependency-tree diff, permission-manifest validation via the ajv already pinned in 25.2-05) covers D-04..D-06. The `ToolRegistryManifest` is a startup-built JSON document (tool_name, provider_package, schema_hash, permission, domain, enabled) that the 25.2-05 session factory consumes as its allowlist source; same-name tools exit the process before it listens. The MCP spike's boundary proof is a negative-test matrix: no internal URL can enter the allowlist, `external_evidence` artifacts carry `prohibited_from_canon=true`, and the 25.2-03 finalizer's manifest-validation gate rejects external evidence in cited answers.

**Primary recommendation:** Build `agent-service/src/governance/` (lockfile verifier + static scanner + permission-manifest validator + ToolRegistryManifest builder, all fail-closed at startup), a clean-room domain-action policy core `agent-service/src/policy/` reusing pi-permission-system's documented semantics with Web `ApprovalRequest` round-trips through the 25.2-03 approval API shape, run `pi-mcp-adapter` only via isolated `createMcpAdapter({config})` for the `research-external-context` skill shape, and treat pi-web-ui as a pattern source for a React `CitedAnswerArtifact` renderer — never a dependency.

- D-01: Three-layer adoption — official Pi runtime packages are direct dependencies;
  community infrastructure is reused only via adapter or fork; workflow/memory-style
  packages are pattern-only (redesigned onto NovelMind data models, never installed).
- D-02: Every package receives a recorded verdict: `adopt` / `fork` / `pattern-only` /
  `reject`, captured in a `PackageQualificationReport` (source/version/commit, license,
  dependency tree, lifecycle scripts, registered tools, filesystem/network behavior,
  compatibility result, adoption verdict).
- D-03: Current verdicts (from issue research, re-validated at execution):
  `@earendil-works/pi-agent-core`, `pi-ai`, `pi-coding-agent` SDK = adopt (already 25.2);
  `pi-mcp-adapter` = conditional adopt (external tools only); `@gotgenes/pi-permission-system`

  only); `pi-subagents` = deferred; `pi-acp` = dev tool only; `pi-memory`,

  PostgreSQL); `pi-web-ui` = selective (renderer patterns, not ChatPanel/IndexedDB SSOT);
  large forks/all-in-one bundles/TUI packages/shell-capable packages = reject.

#### Package governance
- D-04: No dynamic `pi install` / `pi update` inside the formal agent service. Distribution
  layout: `agent-service/{packages.lock.json, vendor/pi-packages/, adapters/, extensions/,
  skills/}`; exact npm version or Git SHA pinning; CI lockfile; `npm ci --ignore-scripts`;
  unknown lifecycle scripts never run; every upgrade re-runs API/permission/tool-collision
  tests; user-global `~/.pi` packages never loaded; ResourceLoader allowlist loads only
  declared resource types.

  `package: {network: deny|allowlist, filesystem: deny, shell: deny, env: deny,

- D-06: Startup `ToolRegistryManifest` records `tool_name`, `provider_package`,
  `schema_hash`, `permission`, `domain`, `enabled`; same-name tools fail closed at
  startup — never silent override by load order.

#### External tools and evidence
- D-07: `pi-mcp-adapter` connects only allowlisted external MCP servers (web research,
  external documents, image generation services); lazy discovery via its proxy tool; no
  ambient user-machine MCP config; no other MCP extensions co-loaded.
- D-08: MCP never touches NovelMind PostgreSQL, Original Canon writes, evidence validation
  or core Reader Chat retrieval — internal core tools stay typed FastAPI APIs.
- D-09: External results materialize as `external_evidence` artifacts (sources,
  retrieval_time, claims, confidence, `prohibited_from_canon=true`) and are never mixed
  with `original_text_evidence`.

#### Permission policy and approval
- D-10: Policy core adapts the `@gotgenes/pi-permission-system` allow/ask/deny model to
  domain actions (not file paths), e.g. `search_original_text: allow`,
  `create_scene_spec_candidate: allow`, `generate_image_candidate: ask`,
  `publish_illustration: ask`, `create_canon_fork: ask`,
  `modify_original_canon: deny`, `move_active_pointer: deny`.
- D-11: `allow` executes directly; `ask` creates a Web `ApprovalRequest` confirmed in the
  frontend (not a TUI); `deny` blocks deterministically. Reused concepts: rule precedence,
  fail-closed, tool-visibility filtering, session-scoped approval, skill/MCP layered
  permissions.

#### Extension patterns
- D-12: Small official/community extension patterns (permission-gate, protected-paths,
  confirm-destructive, question/questionnaire, todo, notify, slow-mode/review-gate,
  custom compaction preserving Evidence/Decision/Artifact IDs, event bus) are rewritten
  as internal extensions — never loaded as generic versions with file/shell power.

#### Gating and non-goals
- D-13: Execution of this phase starts only after the Phase 22 three-consecutive-green

- D-14: Non-goals — no arbitrary package installation; no multi-agent; no third-party

### Pattern 1: `packages.lock.json` governance lock manifest (D-04)
**What:** a committed JSON document that is the *governance* layer on top of npm's `package-lock.json` (which remains the CI lockfile). npm owns integrity; the manifest owns verdicts, provenance and permissions.
**When to use:** loaded by CI (`verify-lockfile.mjs`) and at agent-service startup before anything else.
**Format (Claude's discretion — recommended):**
```jsonc
{
  "version": 1,
  "generated_by": "25.3-01",
  "packages": [
    {
      "name": "pi-mcp-adapter",
      "version": "2.17.0",                 // exact pin — no ranges
      "source": "npm",                      // "npm" | "git"
      "integrity": "sha512-...",            // must equal package-lock.json entry
      "verdict": "adopt",                   // adopt | fork | pattern-only | reject (D-02)
      "scope": "external-tools-only",       // D-03 condition recorded
      "qualification_report": "qualification/pi-mcp-adapter.md",
      "permission_manifest": {
        "network": "allowlist",             // deny | allowlist
        "network_allowlist": ["mcp.external-research.example"],
        "filesystem": "deny", "shell": "deny", "env": "deny",
        "secrets": "named-only",
        "tools": ["mcp"],                   // proxy tool only (D-07)
        "artifact_writes": ["external_evidence"]
      }
    },
    { "name": "@gotgenes/pi-permission-system", "version": "24.0.0",
      "source": "npm", "verdict": "pattern-only", "installed": false,
      "qualification_report": "qualification/gotgenes-pi-permission-system.md" }
  ]
}
```
Rules enforced by `verify-lockfile.mjs` + startup `lockfile.ts`: every **installed** runtime dependency of agent-service has a manifest entry with a non-`reject` verdict and a D-05 permission manifest; every entry's `version`+`integrity` matches `package-lock.json` exactly; any `adopt` package lacking a qualification report fails the gate. Unknown lifecycle scripts never run because installs are always `npm ci --ignore-scripts` — the scanner additionally asserts the dependency closure declares zero `preinstall`/`install`/`postinstall` scripts, so `--ignore-scripts` is proven, not assumed.

### Pattern 2: Static scanner tooling (D-04, Claude's discretion — decided)
**What:** `agent-service/scripts/scan-packages.mjs` orchestrating four checks, all offline-capable except audit:
1. **License:** `license-checker-rseidelsohn --json` over the closure; allowlist `MIT|BSD-*|ISC|Apache-2.0`; anything else (or UNKNOWN) fails.
2. **Vulnerabilities:** `npm audit --json` — fail on `critical`/`high` in runtime deps.
3. **Provenance:** `npm audit signatures` — registry signature verification for every package [CITED: npm CLI docs, npm ≥8].
4. **Lifecycle scripts:** walk `npm ls --json --all`, read each installed `node_modules/<pkg>/package.json`, fail if any `scripts.preinstall|install|postinstall` exists.
5. **Dependency-tree diff:** the closure set must equal the union of `packages.lock.json` entries' declared trees — an undeclared transitive newcomer (dependency confusion signal) fails.
**Why this stack:** every primitive is registry-native or one maintained package; no hosted service, no account, no new runtime dependency (scanner is dev-only). Mirrors the repo's `tests/ci` static-gate philosophy (pure source scanning, `pytest.mark.unit`, seconds-fast).

### Pattern 3: Startup ToolRegistryManifest + fail-closed collision gate (D-06)
**What:** at startup, after lockfile verification, build the manifest from the 25.2-05 tool registry (`DOMAIN_TOOL_NAMES`), each loaded skill's `allowed_tools`, and — when the MCP adapter is enabled — the single `mcp` proxy entry. `schema_hash` = sha256 of the tool's TypeBox JSON schema (canonicalized). Then the collision gate.
**Example:**
```typescript
// agent-service/src/governance/tool-registry-manifest.ts
export interface ToolRegistryEntry {
  tool_name: string; provider_package: string;  // "agent-service" | "pi-mcp-adapter" | skill name
  schema_hash: string; permission: "allow" | "ask" | "deny";
  domain: string;                               // "novel-read" | "external-research" | ...
  enabled: boolean;
}
export function buildToolRegistryManifest(sources: ToolRegistryEntry[][]): ToolRegistryEntry[] {
  const seen = new Map<string, ToolRegistryEntry>();
  for (const entry of sources.flat()) {
    const prior = seen.get(entry.tool_name);
    if (prior) {                                  // D-06: fail closed — never load-order override
      throw new ToolCollisionError(
        `tool_name collision: "${entry.tool_name}" from ${prior.provider_package} and ${entry.provider_package}`);
    }
    seen.set(entry.tool_name, entry);
  }
  return [...seen.values()];
}
// Startup chain (before server.listen): verifyLockfile() → validatePermissionManifests()
//   → buildToolRegistryManifest(...) → session factory consumes the manifest as its
//   `tools` allowlist source (superset check vs DOMAIN_TOOL_NAMES stays from 25.2-05).
```
**Plug points into 25.2:** the session factory's `tools:` allowlist and the skill loader's `DOMAIN_TOOL_NAMES` subset check both read from this manifest instead of a bare constant (single source, same fail-closed direction); the ResourceLoader allowlist (25.2-05 `resource-loader.ts`) loads only resource types declared in `packages.lock.json` (D-04).

### Pattern 4: Domain-action permission policy core (D-10/D-11) — clean-room, semantics from pi-permission-system
**What:** a small engine evaluating `allow|ask|deny` over **domain actions** (not file paths/bash). Reused concepts, all documented in the upstream configuration reference [CITED: gotgenes/pi-packages configuration.md]:
- *Universal fallback defaults to `ask`* (least privilege); NovelMind hardens to a frozen explicit table where unknown actions resolve `deny` (fail-closed, matching `modify_original_canon: deny`).
- *Last-match-wins within an ordered rule list; most-restrictive-wins across layers* (`deny > ask > allow`) — layers here: global policy → per-skill `approval_required_for` → session-scoped approvals.
- *Invalid higher-precedence scope fails closed* (clamp `allow`→`ask` on load error).
- *Session-scoped approval* ("approve once" vs "approve for session").
- *Tool-visibility filtering is restrict-only*: the active tool set starts from the session's allowed tools and only ever shrinks for denied/disabled entries.
- *Unknown/unregistered tools blocked before permission checks*.
**Policy table (D-10 seed, frozen in code + mirrored in tests):**
```typescript
// agent-service/src/policy/engine.ts
export type PolicyAction = "allow" | "ask" | "deny";
export interface DomainActionRule { action: string; policy: PolicyAction; reason?: string }
export const DOMAIN_ACTION_POLICY: readonly DomainActionRule[] = [
  { action: "search_original_text",        policy: "allow" },
  { action: "create_scene_spec_candidate", policy: "allow" },
  { action: "generate_image_candidate",    policy: "ask" },
  { action: "publish_illustration",        policy: "ask" },
  { action: "create_canon_fork",           policy: "ask" },
  { action: "modify_original_canon",       policy: "deny", reason: "Original Canon is read-only for agents (D-14)" },
  { action: "move_active_pointer",         policy: "deny", reason: "Active-pointer cutover requires explicit authorization" },
] as const;
export function evaluate(action: string, ctx: { skillRules?: DomainActionRule[]; sessionApprovals: Set<string> }): PolicyAction {
  if (ctx.sessionApprovals.has(action)) return "allow";          // session-scoped approval (D-11)
  const skill = ctx.skillRules?.find(r => r.action === action);  // per-skill layer
  const global = DOMAIN_ACTION_POLICY.find(r => r.action === action);
  const decisions = [skill?.policy, global?.policy].filter(Boolean) as PolicyAction[];
  if (decisions.includes("deny")) return "deny";                 // most-restrictive-wins
  if (decisions.includes("ask")) return "ask";
  if (decisions.length) return "allow";
  return "deny";                                                 // unknown action: fail closed
}
```
**`ask` → Web ApprovalRequest (D-11):** the engine returns `ask`; the run pauses the gated action and the agent-service POSTs `/api/agent/approval-requests` (FastAPI persists, owner-scoped); the frontend renders it in a `ui/dialog.tsx`-based confirm inside the agent workspace (SSE `approval_request` frame); the user's confirm/reject POSTs back; on confirm the action proceeds (optionally recorded in `sessionApprovals` for the run), on reject it resolves as denied. Server-side, the FastAPI endpoint is the authority — the web UI never decides, mirroring the 25.2-03 artifact approve/reject shape.
**Fork-vs-clean-room recommendation (Claude's discretion — decided): clean-room.** Rationale: (1) upstream's engine is inseparable from Pi hooks (`before_agent_start`/`tool_call`/`input`), TUI keybind dialogs and `~/.pi` config files — none exist in the web product; (2) its matching machinery targets bash command decomposition (tree-sitter) and filesystem paths — domain actions need none of it; (3) the fork would import `web-tree-sitter` native/WASM weight for zero benefit; (4) the *documented semantics* (the actual value) are ~250 lines to reimplement and can be pinned by a decision-matrix test suite. This satisfies D-03's "fork/extract policy core" as extraction of the policy model, recorded in the qualification report.

### Pattern 5: MCP isolation via isolated config snapshot (D-07..D-09)
**What:** register pi-mcp-adapter with a fully supplied config — documented as "a complete, isolated snapshot... not merged with files, imports, global config, project config, or `--mcp-config`, and it is never mutated" [CITED: pi-mcp-adapter README, SDK configuration]. Ambient discovery is excluded by construction; keep `hostConfigDiscovery` at its default `"off"` regardless.
**Allowlist config shape:**
```typescript
// agent-service/src/mcp/adapter.ts
import { createMcpAdapter } from "pi-mcp-adapter";
export function buildMcpExtension(cfg: McpAllowlistConfig) {
  return createMcpAdapter({
    config: {
      settings: { hostConfigDiscovery: "off", directTools: false, autoAuth: false },
      mcpServers: Object.fromEntries(cfg.servers.map(s => [s.name, {
        ...(s.transport === "stdio"
          ? { command: s.command, args: s.args }       // pinned binary, no npx @latest
          : { url: s.url }),                            // https only; allowlist-validated
        lifecycle: "lazy",                              // D-07: connect on first tool call
        requestTimeoutMs: 30_000,
        exposeResources: false,
      }])),
    },
  });
}
```
The allowlist itself lives in `packages.lock.json` (governed, reviewable) — **not** in any ambient MCP file. Only the proxy tool is exposed (`directTools: false`): lazy discovery via `mcp({search})` → `mcp({tool, args})` per D-07. No other MCP extension is co-loaded (the ResourceLoader extension list stays exactly the 25.2 inline factories + this one).
**`external_evidence` artifact schema (D-09 fields):**

### Anti-Patterns to Avoid
- **`pi install` / ambient `.mcp.json` at runtime:** D-04/D-07 forbid both; the file-based adapter mode merges user-global configs — use only the isolated `config` snapshot.
- **`directTools: true`:** registers MCP tools as first-class Pi tools from a disk cache, widening the tool surface beyond the proxy and complicating the ToolRegistryManifest — keep the single `mcp` proxy entry.
- **Treating pi-permission-system as a dependency:** its npm package is a Pi extension, not a library — importing it pulls Pi-hook registration and tree-sitter. Extract semantics only (Pattern 4).
- **Installing pi-web-ui:** version drift (0.75.3 vs SDK 0.83.0), heavy/unusual deps (CDN xlsx tarball), and its IndexedDB/provider-key storage model conflicts with D-15 and Next.js/PostgreSQL authority. Borrow renderer patterns; render in React.
- **Prompt-side or client-side permission decisions:** `deny` must be deterministic in the policy engine; approval state round-trips through FastAPI (25.2-04 Must-Have); the SSE frame only notifies.
- **Mixing evidence types:** `external_evidence` never enters `original_text_evidence` manifests, Canon, evidence validation, or core retrieval (D-08/D-09) — enforce in the finalizer, not in prompts.

## Common Pitfalls

### Pitfall 1: Typosquatting / slopsquatting in the Pi ecosystem
**What goes wrong:** a similarly-named package (`pi-mcp-adaptor`, unscoped variants) gets installed; 25.2 research already caught the unscoped `pi-storage-sqlite-node` 404.
**Why it happens:** young ecosystem, many community forks (`@gotgenes/pi-permission-system` is itself a fork of `MasuRii/pi-permission-system`).
**How to avoid:** names only from CONTEXT.md canonical refs; `npm view` + slopcheck + official-repo cross-check before every install (the Package Legitimacy Gate); `packages.lock.json` records exact name+version+integrity; scanner fails on undeclared transitive packages.
**Warning signs:** qualification report's repository URL doesn't match the canonical ref; download counts near zero.

### Pitfall 2: Lifecycle scripts executing at install
**What goes wrong:** a dependency's `postinstall` runs network/file system code on dev machines and CI.
**Why it happens:** `npm install` runs them by default; one transitive package is enough.
**How to avoid:** `npm ci --ignore-scripts` everywhere (D-04) + scanner assertion that the closure declares zero lifecycle scripts (so the flag is proven sufficient); `@napi-rs/keyring` (pi-mcp-adapter transitive) ships prebuilds — verify no `install` script is required for it on Windows, else pin and document the exception in the qualification report (fail-closed: exception requires human sign-off).
**Warning signs:** install output showing script execution; scanner diff finding new `scripts` fields after an upgrade.

### Pitfall 3: Version drift between official Pi packages
**What goes wrong:** pi-web-ui 0.75.3 expects `^0.75.3` pi-ai/pi-tui while the runtime pins 0.83.0 — duplicated/conflicting SDK copies if installed together.
**Why it happens:** earendil-works publishes packages on independent cadences.
**How to avoid:** pi-web-ui is never installed (pattern-only); the runtime keeps the single 0.83.0 SDK line; the lockfile verifier asserts one version per `@earendil-works/*` package across the closure; every upgrade re-runs the API/permission/tool-collision suites (D-04).
**Warning signs:** two versions of a Pi package in `npm ls`; type errors at the adapter boundary.

### Pitfall 4: Collision-gate false positives blocking legitimate tools
**What goes wrong:** a namespaced MCP tool (`server_tool`) or a renamed domain tool trips the same-name gate and blocks startup after a routine upgrade.
**Why it happens:** the proxy tool exposes remote names inside `mcp({tool})` args, not as registered tools — confusion about which namespace the gate covers.
**How to avoid:** the gate covers the **Pi-registered tool namespace only** (domain tools + `mcp` proxy + extension tools); MCP remote names live behind the proxy and are governed by the server allowlist instead. Manifest entries carry `provider_package` so the error message names both parties; adversarial tests inject duplicates deliberately to tune messages.
**Warning signs:** startup `ToolCollisionError` after a dependency bump with no code change.

### Pitfall 5: Windows dev environment friction (carried from 25.2, extended)
**What goes wrong:** Docker daemon down (verified not running 2026-08-01); native deps (`@napi-rs/keyring`) needing prebuilds; Git Bash vs PowerShell path drift; GBK console issues in Python tooling.
**How to avoid:** governance scripts are plain Node (no native builds); MCP spike servers run via stdio with pinned binaries or HTTP URLs — both work on Windows; start Docker Desktop + `docker compose up -d db` before backend-touching tests; the adapter's keyring/OAuth features stay disabled (permission manifest denies `secrets` beyond named-only), avoiding the native path entirely in practice.
**Warning signs:** `node-gyp` output at install; ECONNREFUSED 5432 during isolation tests.

### Pitfall 6: `external_evidence` leaking into cited answers
**What goes wrong:** the agent cites an MCP-sourced claim as if it were novel text; Canon contamination via copy-paste into candidate artifacts.
**Why it happens:** the model can't distinguish evidence classes unless the pipeline does.
**How to avoid:** type separation at the schema level (`type: "external_evidence"` vs `original_text_evidence`), finalizer validation rejecting external refs in cited answers, `prohibited_from_canon` written server-side, and the negative-test matrix (Pattern 5 / Validation Architecture) running every axis.
**Warning signs:** an artifact with both evidence classes; a cited answer whose manifest contains a `mcp://` or external URI ref.

### Pitfall 7: pi-mcp-adapter is a TypeScript-source package
**What goes wrong:** `import "pi-mcp-adapter"` fails under raw Node ESM — the package ships TS source for Pi's source-loader [CITED: README "SDK configuration"].
**Why it happens:** raw Node ESM does not execute the `.ts` entry directly.
**How to avoid:** agent-service already compiles TS (25.2-05 `tsc --noEmit` + vitest); run the service through a TS-capable loader (`node --import tsx` per README) or import via the project's own TS build — decide at execution, record in the plan SUMMARY.
**Warning signs:** `ERR_UNKNOWN_FILE_EXTENSION` at startup.

| Supply chain (outside ASVS numbering; primary threat domain) | yes | Package Legitimacy Gate + Pattern 2 scanner + `npm ci --ignore-scripts` + vendored tarballs |

### Known Threat Patterns for {npm supply chain + MCP + policy engine}
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Typosquatted/slopsquatted Pi package | Tampering | names from canonical refs only; slopcheck + npm view + repo cross-check; lockfile integrity (Pitfall 1) |
| Malicious lifecycle script at install | Tampering / EoP | `npm ci --ignore-scripts`; scanner proves zero scripts in closure (Pitfall 2) |
| Dependency confusion (undeclared transitive) | Tampering | dep-tree diff vs packages.lock.json; exact pins, no ranges |
| MCP server reaching internal network/DB | EoP / Info Disclosure | URL allowlist validation (https, no private IPs); stdio allowlist of pinned binaries; no DB env in adapter config; negative tests (25.3-03) |
| External evidence laundered into Canon | Tampering | `prohibited_from_canon` server-side constant; finalizer manifest gate rejects external refs (D-08/D-09) |
| Approval forgery (client self-approves) | Tampering | approval state only via FastAPI endpoints with owner check; SSE frame is notification, not authority |
| Policy bypass via unregistered tool/action | EoP | unknown tools blocked before permission checks; unknown actions resolve `deny`; collision gate fails startup |
| Prompt injection steering MCP tool selection | Tampering | proxy-only surface; per-server `includeTools` unused; external results are data (artifact), never evidence authority |
| Version drift smuggling a second SDK copy | Tampering | lockfile verifier asserts single-version-per-package across `@earendil-works/*` (Pitfall 3) |
