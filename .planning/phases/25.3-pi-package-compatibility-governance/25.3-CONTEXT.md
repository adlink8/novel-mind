# Phase 25.3: Pi Package Compatibility and Governance - Context

**Gathered:** 2026-08-01
**Status:** Ready for planning
**Source:** PRD Express Path (GitHub Issue #29 package-research comment 2026-08-01T03:02Z, section "对 Issue #29 路线图的修订建议" — locked user decisions)

<domain>
## Phase Boundary

Establish the controlled reuse mechanism for Pi ecosystem packages on top of the Phase 25.2
agent runtime, and prove that third-party extensions cannot bypass NovelMind's permission,
evidence, Canon and Artifact boundaries. Delivers: package lock/audit pipeline, startup
Tool Registry Manifest with fail-closed collision gate, an isolated pi-mcp-adapter
external-tool spike, a domain-action permission policy core with Web Approval, and a
pi-web-ui renderer feasibility verdict.

Out of scope: dynamic package installation at runtime, multi-agent, third-party memory
systems, any extension shell/host-filesystem/database access, any third-party write to
Original Canon.

</domain>

<decisions>
## Implementation Decisions

### Adoption model
- D-01: Three-layer adoption — official Pi runtime packages are direct dependencies;
  community infrastructure is reused only via adapter or fork; workflow/memory-style
  packages are pattern-only (redesigned onto NovelMind data models, never installed).
- D-02: Every package receives a recorded verdict: `adopt` / `fork` / `pattern-only` /
  `reject`, captured in a `PackageQualificationReport` (source/version/commit, license,
  dependency tree, lifecycle scripts, registered tools, filesystem/network behavior,
  compatibility result, adoption verdict).
- D-03: Current verdicts (from issue research, re-validated at execution):
  `@earendil-works/pi-agent-core`, `pi-ai`, `pi-coding-agent` SDK = adopt (already 25.2);
  `pi-mcp-adapter` = conditional adopt (external tools only); `@gotgenes/pi-permission-system`
  = fork/extract policy core; `pi-web-access` = later conditional (ExternalResearchArtifact
  only); `pi-subagents` = deferred; `pi-acp` = dev tool only; `pi-memory`,
  `@remnic/plugin-pi` = pattern-only; `@oh-my-pi/omp-stats` = pattern-only (metrics into
  PostgreSQL); `pi-web-ui` = selective (renderer patterns, not ChatPanel/IndexedDB SSOT);
  large forks/all-in-one bundles/TUI packages/shell-capable packages = reject.

### Package governance
- D-04: No dynamic `pi install` / `pi update` inside the formal agent service. Distribution
  layout: `agent-service/{packages.lock.json, vendor/pi-packages/, adapters/, extensions/,
  skills/}`; exact npm version or Git SHA pinning; CI lockfile; `npm ci --ignore-scripts`;
  unknown lifecycle scripts never run; every upgrade re-runs API/permission/tool-collision
  tests; user-global `~/.pi` packages never loaded; ResourceLoader allowlist loads only
  declared resource types.
- D-05: Every loaded package declares a permission manifest:
  `package: {network: deny|allowlist, filesystem: deny, shell: deny, env: deny,
  secrets: named-only, tools: [], artifact_writes: []}` — a package that cannot declare
  its permissions does not enter the service.
- D-06: Startup `ToolRegistryManifest` records `tool_name`, `provider_package`,
  `schema_hash`, `permission`, `domain`, `enabled`; same-name tools fail closed at
  startup — never silent override by load order.

### External tools and evidence
- D-07: `pi-mcp-adapter` connects only allowlisted external MCP servers (web research,
  external documents, image generation services); lazy discovery via its proxy tool; no
  ambient user-machine MCP config; no other MCP extensions co-loaded.
- D-08: MCP never touches NovelMind PostgreSQL, Original Canon writes, evidence validation
  or core Reader Chat retrieval — internal core tools stay typed FastAPI APIs.
- D-09: External results materialize as `external_evidence` artifacts (sources,
  retrieval_time, claims, confidence, `prohibited_from_canon=true`) and are never mixed
  with `original_text_evidence`.

### Permission policy and approval
- D-10: Policy core adapts the `@gotgenes/pi-permission-system` allow/ask/deny model to
  domain actions (not file paths), e.g. `search_original_text: allow`,
  `create_scene_spec_candidate: allow`, `generate_image_candidate: ask`,
  `publish_illustration: ask`, `create_canon_fork: ask`,
  `modify_original_canon: deny`, `move_active_pointer: deny`.
- D-11: `allow` executes directly; `ask` creates a Web `ApprovalRequest` confirmed in the
  frontend (not a TUI); `deny` blocks deterministically. Reused concepts: rule precedence,
  fail-closed, tool-visibility filtering, session-scoped approval, skill/MCP layered
  permissions.
- D-15: The downstream domain-action vocabulary is frozen and fail-closed:
  `publish_illustration`, `attach_illustration_to_text`, `create_canon_fork`,
  `apply_derivative_edit`, `publish_derivative_revision`, `allow_divergence`,
  `publish_derivative_visual`, `prepare_export`, `approve_export`,
  `materialize_export`, and `download_export`. Unknown actions deny. Every
  ApprovalRequest binds run_id, skill_version_id, artifact_id/revision_id, owner_id,
  novel_id, branch_id/fork_id when applicable, action, payload_hash, expiry and decision
  actor/time. Original Canon mutation and active-pointer movement remain permanent deny.

### Extension patterns
- D-12: Small official/community extension patterns (permission-gate, protected-paths,
  confirm-destructive, question/questionnaire, todo, notify, slow-mode/review-gate,
  custom compaction preserving Evidence/Decision/Artifact IDs, event bus) are rewritten
  as internal extensions — never loaded as generic versions with file/shell power.

### Gating and non-goals
- D-13: Execution of this phase starts only after the Phase 22 three-consecutive-green
  scheduled gate closes; planning artifacts may proceed now.
- D-14: Non-goals — no arbitrary package installation; no multi-agent; no third-party
  memory replacing Narrative Memory; no extension receives shell, host-filesystem or
  direct database permissions; no third-party tool may modify Original Canon.

### the agent's Discretion
- Lockfile format details and vendor directory layout under `agent-service/`.
- Static scanner implementation (license/dependency/lifecycle) — tooling choice.
- Policy core fork vs clean-room reimplementation of the precedence engine.
- ApprovalRequest UX details inside the existing web app.
- Renderer feasibility prototype scope (one artifact type).

</decisions>

<specifics>
## Specific Ideas

- `PackageQualificationReport` is produced per evaluated package and stored under
  `.planning/` or `agent-service/qualification/` as the adoption evidence.
- Startup sequence: load lockfile → verify pins → scan permissions → build
  ToolRegistryManifest → collision check → only then start the session loop.
- External-research Skill (`research-external-context`) is the only MCP consumer shape;
  its output artifact carries `prohibited_from_canon=true`.
- Removing any single community package must leave core reading QA functional (phase
  verification criterion).

</specifics>

<deferred>
## Deferred Ideas

- `pi-web-access` external research skill (post-core-QA).
- `pi-subagents` reviewer/judge roles (only after single-agent failure is proven on a
  frozen task set).
- `pi-acp` Zed/ACP debugging adapter (developer tooling, never core runtime).
- `pi-memory` / `@remnic/plugin-pi` operational-memory designs (pattern borrowing only).
- `@oh-my-pi/omp-stats` dashboard (metrics model into NovelMind PostgreSQL instead).
- D-12 extension patterns not needed by this phase's vertical slices — question /
  questionnaire, todo, notify, and custom-compaction (preserving Evidence/Decision/
  Artifact IDs) — are intentionally deferred to the workspace/derivative phases that
  consume them; the rest of D-12 is dispositioned in 25.3-02 (ResourceLoader allowlist
  clause) and 25.3-04 (permission-gate, confirm-destructive/review-gate, event bus)
  "Decision traceability" notes (revision 2026-08-01).

</deferred>
