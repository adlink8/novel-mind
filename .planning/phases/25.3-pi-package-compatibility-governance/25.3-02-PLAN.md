<objective>
Build the startup governance chain (D-05/D-06): the `ToolRegistryManifest` — a startup-built
JSON document recording tool_name, provider_package, schema_hash, permission, domain,
enabled for every tool the service can expose — plus the permission-manifest validator and
the fail-closed collision gate that kills the process before it listens when two providers
claim the same tool name or a package cannot declare its permissions.

Purpose: REQ-AGENT-05's "tool-name collisions fail closed at startup" and D-05's "a package
that cannot declare its permissions does not enter the service" are startup-time properties;
this plan makes the 25.2-05 session factory draw its allowlist from the manifest so there is
one source of truth for what the agent may call.

Output: `agent-service/src/governance/{lockfile,permission-manifest,tool-registry-manifest}.ts`
+ startup wiring in `server.ts` + session-factory consumption + `tests/governance.test.ts`
adversarial matrix.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| packages.lock.json + skill.yaml (disk) -> startup loaders | Code-adjacent config; a forged entry could smuggle a tool or weaken permissions — validation is fail-closed before any session use |
| extension/skill tool registrations -> Pi tool namespace | Third-party code can attempt to shadow a domain tool by registering the same name |
| ToolRegistryManifest -> session factory | The allowlist is the choke point for every tool the agent may call; a leak here bypasses all downstream checks |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25.3-02-01 | Elevation of Privilege | tool-name collision/shadowing — an extension or skill silently overrides a domain tool by load order | mitigate | D-06 collision gate: seen-map over all sources throws ToolCollisionError naming both provider_packages; process exits before listen; adversarial tests inject duplicates across every source pair (domain/skill/extension) |
| T-25.3-02-02 | Elevation of Privilege | extension with undeclared permissions entering the service | mitigate | D-05: validatePermissionManifests refuses startup for any installed entry missing/invalidating the manifest; filesystem/shell/env clamped to literal "deny", secrets to "named-only"; tests assert refusal names the missing field |
| T-25.3-02-03 | Tampering | schema drift — a tool's schema silently changing under the agent (upgrade smuggling new parameters) | mitigate | sha256 schema_hash over canonicalized TypeBox JSON recorded per entry; drift test rehashes a mutated schema and asserts detection at startup |
| T-25.3-02-04 | Elevation of Privilege | disabled tool reaching a session anyway | mitigate | factory allowlist derives from enabled manifest entries only; test asserts a disabled entry never appears; subset defense-in-depth throw retained from 25.2-05 |
| T-25.3-02-05 | Denial of Service | collision-gate false positives blocking legitimate startup after routine upgrades | accept-with-guard | Gate covers the Pi-registered namespace only; MCP remote names live behind the proxy allowlist (Pitfall 4); false-positive test (similar distinct names start fine) prevents over-broad matching; error messages name both parties so operators can fix the genuine collision fast |
| T-25.3-02-06 | Tampering | manifest builder bypassed by a future code path reading DOMAIN_TOOL_NAMES directly | mitigate | drift-guard test asserts the factory allowlist derives from the manifest (single-source mirror test house pattern); session-factory grep acceptance criterion forbids the direct read |
| T-25.3-SC | Tampering | npm installs | mitigate | None this plan — reuses 25.2-05 pins (ajv, ajv-formats, yaml); acceptance criterion asserts package.json unchanged for Task 1; any future install goes through the 25.3-01 Package Legitimacy Gate |
</threat_model>
